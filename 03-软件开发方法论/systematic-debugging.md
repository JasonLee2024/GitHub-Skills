# 系统化调试方法论

> 本文档基于 Hermes Agent 的 `systematic-debugging` 技能整理，介绍一种从根因排查到修复验证的四阶段调试框架。

## 概述

系统化调试是一种**基于证据、根因优先**的调试方法论。它的核心信条是：

**没有找到根因之前，不要尝试修复。症状修复等于失败。**

与"猜测-尝试-再猜测"的随机调试不同，系统化调试遵循四个严格的阶段：

```
阶段 1: 根因调查  →  阶段 2: 模式分析  →  阶段 3: 假设验证  →  阶段 4: 修复实现
```

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
（不找到根因，就不修复）
```

如果没有完成阶段 1（根因调查），就不能提出修复方案。

## 何时使用

**任何技术问题**都应当使用系统化调试：

- 测试失败
- 生产环境 bug
- 非预期的行为
- 性能问题
- 构建失败
- 集成问题

**特别需要在以下场景使用：**
- 时间压力大（紧急情况下更容易猜测）
- "快速修复一下"看起来很诱人
- 已经尝试了多个修复没效果
- 前一个修复不管用
- 你并不完全理解问题

**不要跳过的情况：**
- 问题看起来很"简单"（简单的 bug 也有根因）
- 你赶时间（着急必然导致返工）
- 有人要求"马上修好"（系统化比瞎猜快）

## 阶段 1：根因调查

**在尝试任何修复之前，必须先做这一步。**

### 1.1 仔细阅读错误消息

- 不要跳过错误或警告
- 它们经常包含精确的解决方案
- 完整阅读堆栈跟踪
- 记下行号、文件路径、错误码

**操作：** 使用 `read_file` 读取相关源文件。使用 `search_files` 在代码库中搜索错误字符串。

### 1.2 稳定重现

- 能否稳定触发？
- 精确的重现步骤是什么？
- 每次都出现吗？
- 如果不能稳定重现 → 收集更多数据，不要猜测

**操作：** 使用 `terminal` 运行失败测试或触发 bug：

```bash
pytest tests/test_module.py::test_name -v
```

### 1.3 检查最近的变更

- 什么变更可能导致这个问题？
- git diff、最近的 commit
- 新依赖、配置变更

**操作：**

```bash
git log --oneline -10
git diff
git log -p --follow src/problematic_file.py | head -100
```

### 1.4 在多组件系统中收集证据

**当系统有多个组件（API → 服务 → 数据库、CI → 构建 → 部署）时：**

在提出修复方案之前，先添加诊断工具：

对于每个组件边界：
- 记录进入组件的数据
- 记录退出组件的数据
- 验证环境和配置的传递
- 检查各层的状态

运行一次以收集证据，证明哪里出了问。然后分析证据，找出故障组件。最后深入调查该组件。

### 1.5 追溯数据流

**当错误在调用栈深处时：**

- 异常值从哪里来？
- 谁用异常值调用了这个函数？
- 不断向上追溯，直到找到源头
- 修复源头，而非症状

**操作：** 使用 `search_files` 追溯引用：

```python
search_files("function_name(", path="src/", file_glob="*.py")
search_files("variable_name\\s*=", path="src/", file_glob="*.py")
```

### 阶段 1 完成检查清单

- [ ] 错误消息完整阅读并理解
- [ ] 问题被稳定重现
- [ ] 最近的变更已识别并审查
- [ ] 证据已收集（日志、状态、数据流）
- [ ] 问题已定位到特定的组件/代码
- [ ] 根因假设已经形成

**停止：** 在理解"为什么"之前，不要进入阶段 2。

## 阶段 2：模式分析

**在动手修复之前，先找到模式：**

### 2.1 寻找工作的例子

- 在同一个代码库中找到类似的工作代码
- 什么工作正常，且与被破坏的代码相似？

### 2.2 对照参考实现

- 如果是在实现某个模式，完整阅读参考实现
- 不要跳读——逐行阅读
- 在应用之前彻底理解模式

### 2.3 识别差异

- 工作版本和损坏版本之间有什么不同？
- 列出每一个差异，无论多小
- 不要假设"那个不重要"

### 2.4 理解依赖

- 这个组件需要哪些其他组件？
- 需要什么设置、配置、环境？
- 它做了哪些假设？

## 阶段 3：假设验证

**遵循科学方法：**

### 3.1 建立单一假设

- 清晰说明："我认为 X 是根因，因为 Y"
- 写下来
- 具体明确，不要含糊

### 3.2 最小化测试

- 做**尽可能小的**改动来验证假设
- 一次只改变一个变量
- 不要一次性修复多个问题

### 3.3 验证后再继续

- 有效了？→ 进入阶段 4
- 没效果？→ 建立新假设
- 不要在上一个修复失败后叠加更多修复

### 3.4 不懂就说不懂

- 说"我不理解 X"
- 不要假装懂
- 向用户求助
- 继续研究

## 阶段 4：修复实现

**修复根因，而不是症状：**

### 4.1 创建失败测试用例

- 最简单的复现方式
- 尽可能自动化测试
- **必须在修复之前完成**
- 使用 TDD（测试驱动开发）技能

### 4.2 实现单一修复

- 解决已确定的根因
- **一次只改一个地方**
- 不做"顺便改进"或附带重构

### 4.3 验证修复

```bash
# 运行回归测试
pytest tests/test_module.py::test_regression -v

# 运行全部测试——确认无回归
pytest tests/ -q
```

### 4.4 如果修复不生效——规则三原则

- **停下。**
- 计数：已经尝试了几次修复？
- 如果 < 3：回到阶段 1，用新信息重新分析
- **如果 ≥ 3：停下，质疑架构（下一步）**
- 不要在没有架构讨论的情况下尝试第 4 次修复

### 4.5 3 次修复失败后：质疑架构

**表明架构问题的模式：**
- 每次修复都在不同地方暴露新的共享状态/耦合
- 修复需要"大规模重构"才能实现
- 每次修复都在其他地方引发新症状

**停下，质疑基础：**
- 这个模式本质上合理吗？
- 我们是否因为"惯性"而坚持？
- 是否应该重构架构，而不是继续修复症状？

**在尝试更多修复前与用户讨论。**

这不是假设失败——而是架构选择错误。

## 红旗警告

如果你发现自己在想以下任何一点，请停下并遵循流程：

- "先快速修复，后面再调查"
- "改 X 试试看能不能行"
- "同时改多个地方，然后跑测试"
- "跳过测试，我会手动验证"
- "可能是 X，让我修一下"
- "我不完全理解但这么改可能有用"
- "模式说 X 但我换种方式实现"
- "主要问题是：[列出修复，而不是调查]"
- 在追溯数据流之前就开始提方案
- **"再试一次"（已经试了 2 次以上）**
- **每次修复都在不同地方暴露新问题**

**所有这些都意味着：停下。回到阶段 1。**

**如果 3+ 次修复失败：** 质疑架构（阶段 4 步骤 5）。

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| **1. 根因** | 读错误、重现、检查变更、收集证据、追溯数据流 | 理解 WHAT 和 WHY |
| **2. 模式** | 找工作例子、对比、识别差异 | 知道差异在哪里 |
| **3. 假设** | 建立理论、最小化测试、一次只变一个 | 确认或新假设 |
| **4. 修复** | 创建回归测试、修复根因、验证 | bug 解决，全部通过 |

## 实际效果

来自实际调试案例的数据：
- 系统化方法：15-30 分钟修复
- 随机修复方法：2-3 小时胡乱尝试
- 首次修复成功率：95% vs 40%
- 引入新 bug：接近零 vs 常见

**没有捷径。没有猜测。系统化永远胜出。**

## 与其它方法论的关系

- **TDD**：在修复 bug 时，先写复现 bug 的测试（RED），再修复（GREEN）
- **Writing Plans**：调试结束后，将根因发现记录在计划中
- **Code Review**：验证调试过程中是否遵循了系统化流程
