# 子代理驱动开发 — Subagent-Driven Development

> 本文档基于 Hermes Agent 的 `subagent-driven-development` 技能整理，介绍如何通过分派独立子代理来执行实现计划。

## 概述

子代理驱动开发（Subagent-Driven Development）是一种**通过分派独立的子代理来逐任务执行计划**的开发模式。它的核心理念是：

**每个任务都用全新的子代理 + 两阶段审查（规格合规、代码质量）= 高质量、快迭代。**

## 何时使用

- 你有一个实现计划（来自 Writing Plans 技能或用户需求）
- 任务大多是独立的
- 质量和规格合规很重要
- 希望有自动化的审查环节

## 与手动执行的区别

| 特性 | 子代理驱动 | 手动执行 |
|------|-----------|---------|
| 上下文 | 每个任务全新上下文 | 累积状态可能混淆 |
| 审查 | 自动化的两阶段审查 | 自己审查自己 |
| 质量 | 一致的质量检查 | 依赖当前状态 |
| 沟通 | 子代理可以提问 | 需要主动追问 |

## 核心流程

### 1. 阅读并解析计划

一次性阅读计划文件，提取所有任务及其完整上下文。

不推荐让子代理去读计划文件——直接把完整任务文本放在上下文中。

### 2. 每个任务的工作流

对计划中的每个任务依次执行：

#### Step 1: 分派实现者子代理

使用 `delegate_task`，传递**完整的上下文**：

```
TASK FROM PLAN:
- 创建: src/models/user.py
- 添加 User 类，包含 email (str) 和 password_hash (str) 字段
- 使用 bcrypt 进行密码哈希
- 包含 __repr__ 用于调试

FOLLOW TDD:
1. 写测试文件 tests/models/test_user.py（会失败的测试）
2. 运行: pytest tests/models/test_user.py -v（验证 FAIL）
3. 写最简实现
4. 运行: pytest tests/models/test_user.py -v（验证 PASS）
5. 运行: pytest tests/ -q（验证无回归）
6. 提交: git add -A && git commit -m "feat: add User model"

项目上下文:
- Python 3.11, Flask 应用, src/app.py
- 测试用 pytest, 从项目根目录运行
- bcrypt 已在 requirements.txt 中
```

#### Step 2: 分派规格合规审查者

实现者完成后，对照原始规格验证：

```
CHECK:
- [ ] 所有规格要求都实现了？
- [ ] 文件路径匹配规格？
- [ ] 函数签名匹配规格？
- [ ] 行为符合预期？
- [ ] 没有多余添加（没有 scope creep）？

OUTPUT: PASS 或具体的规格差距清单
```

**如果发现规格问题：** 修复差距，重新审查。规格合规后才能继续。

#### Step 3: 分派代码质量审查者

规格通过后，审查代码质量：

```
CHECK:
- [ ] 遵循项目规范和风格？
- [ ] 合理的错误处理？
- [ ] 变量/函数命名清晰？
- [ ] 测试覆盖充分？
- [ ] 没有明显 bug 或遗漏边界情况？
- [ ] 没有安全问题？

OUTPUT FORMAT:
- 关键问题：[必须修复才能继续]
- 重要问题：[应该修复]
- 次要问题：[可选]
- 结论: APPROVED 或 REQUEST_CHANGES
```

**如果发现质量问题：** 修复后重新审查。

#### Step 4: 标记完成

任务完成后，更新待办清单。

### 3. 最终集成审查

所有任务完成后，分派一个最终的集成审查：

- 所有组件能否协同工作？
- 任务之间是否存在不一致？
- 所有测试通过？
- 是否准备好合并？

### 4. 验证并提交

```bash
pytest tests/ -q
git diff --stat
git add -A && git commit -m "feat: complete [feature name] implementation"
```

## 任务粒度

**每个任务 = 2-5 分钟的工作量。**

**过大：** "实现用户认证系统"

**合适：**
- "创建 User 模型（email 和 password 字段）"
- "添加密码哈希函数"
- "创建登录端点"
- "添加 JWT Token 生成"
- "创建注册端点"

## 处理问题

### 子代理提问怎么办？

- 清晰完整地回答
- 提供额外上下文
- 不要催促

### 审查者发现问题怎么办？

- 实现者子代理（或新的子代理）修复
- 审查者再次审查
- 直到通过为止
- 不要跳过重新审查

### 子代理任务失败怎么办？

- 分派一个新的修复子代理，明确指出哪里出了问题
- 不要在控制器会话中手动修复（会导致上下文污染）

## 绝对不能做的事

- 没有计划就开始实现
- 跳过审查（规格或质量）
- 在有未修复的关键/重要问题时继续前进
- 分派多个实现子代理操作相同文件
- 让子代理自己去读计划文件（应该在上下文中提供）
- 跳过场景设置上下文（子代理需要知道任务在整体中的位置）
- 无视子代理的问题（回答了再让它们继续）
- 接受"差不多符合规格"
- 跳过审查循环（审查者发现问题→实现者修复→再审查）
- 让实现者自己审查代替真实审查（两者都需要）
- **在规格合规未通过之前开始质量审查**（顺序错）
- 在任一审查看待处理问题时进入下一个任务

## 效率原则

**为什么要用全新的子代理？**
- 防止累积的状态污染上下文
- 每个子代理获得干净的、聚焦的上下文
- 不会因之前的代码或推理产生混淆

**为什么两阶段审查？**
- 规格审查早期发现过多或过少实现的问题
- 质量审查确保实现质量达标
- 在问题跨任务积累之前解决

**成本权衡：**
- 更多子代理调用（实现者 + 2个审查者/任务）
- 但早期发现问题（比后期调试复合问题便宜得多）

## 完整流程示例

```
[阅读计划: docs/plans/auth-feature.md]
[创建待办清单，共 5 个任务]

--- 任务 1: 创建 User 模型 ---
[分派实现者子代理]
  子代理: "email 应该是唯一的吗？"
  你: "是的，email 必须唯一"
  子代理: 实现完成, 3/3 测试通过, 已提交。

[分派规格审查者]
  规格审查者: ✅ PASS — 所有要求满足

[分派质量审查者]
  质量审查者: ✅ APPROVED — 干净的代码，好的测试

[标记任务 1 完成]

--- 任务 2: 密码哈希 ---
[分派实现者子代理]
  子代理: 没问题, 实现完成, 5/5 测试通过。

[分派规格审查者]
  规格审查者: ❌ 缺失: 密码强度验证（规格说"最少 8 字符"）

[实现者修复]
  实现者: 已添加验证, 7/7 测试通过。

[重新分派规格审查者]
  规格审查者: ✅ PASS

[分派质量审查者]
  质量审查者: 重要: 魔术数字 8, 提取为常量
  实现者: 提取了 MIN_PASSWORD_LENGTH 常量
  质量审查者: ✅ APPROVED

[标记任务 2 完成]

...(继续所有任务)

[所有任务完成后: 分派最终集成审查]
[运行全部测试: 全部通过]
[完成！]
```

## 与其它方法论的关系

- **Writing Plans**：本技能执行 Writing Plans 产出的计划
- **TDD**：实现者子代理必须遵循 TDD，在上下文中包含 TDD 指令
- **Code Review**：两阶段审查流程本身就是代码审查
- **Systematic Debugging**：子代理遇到 bug 时按系统化调试流程处理
